# AeroSpork comparison — 2026-10-16

## Evidence and limits

Compared [AeroSpork main at f831a600](https://github.com/wbsmolen/aerospork/tree/f831a60072aea7dd81ea704b0a659703a29f8aae), its 72-commit published history and relevant implementation/tests, [AeroSpace main at 74a1bf17](https://github.com/nikitabobko/AeroSpace/tree/74a1bf17e82d70e0a21945ba04bb4f590bf19f83), and the current WinMuxX working tree, including uncommitted changes through build 69. AeroSpork's history starts with a complete 1.0.0 import: there is no preserved AeroSpace ancestor from which to produce an exact historical fork diff. The upstream comparison is therefore against the pinned current tree, with individual fork commits examined where available.

This is a code review of core correctness, performance, persistence, monitors, configuration and tests; it is not an audit of every release/UI change. No runtime code was imported and no installed application was changed. Temporary checkouts were used. AeroSpork passed **129 focused tests**: 98 app tests for focus, native state, AX writes, retries, monitors, performance invariants and workspace memory; then 25 app tests plus 6 common tests for config safety and sockets. No focused test was skipped. These are mock/headless checks, not real DisplayLink, hung-app, gesture or performance measurements.

**Verdict:** useful ideas, with several protections stronger than ours. Importing the fork wholesale would regress important WinMuxX behavior. “Better” below means stronger for the stated property; there is no controlled end-to-end speed comparison.

## Worth adapting

| Priority | Area | Comparison and recommendation |
| --- | --- | --- |
| High | Failed app registration | Their registration has process-launch-aware exponential backoff and schedules bounded follow-up attempts, rather than relying on a click or unrelated refresh. Ours shares an in-flight attempt through a cancellation-aware actor latch, which is already sound, but has no negative backoff or self-scheduled retry. Keep our latch; add an owned retry coordinator keyed by PID and launch identity, cancelled on process exit/config shutdown. Test failed-then-successful launch, cancellation, PID reuse and the absence of later events. [Registration implementation][macapp]; [retry commit][retry]. |
| High | Slow/unresponsive apps | Both preserve windows on `.cannotComplete`; ours also checks native existence. Theirs additionally skips repeated reads of an app that already timed out in a refresh, and preserves native minimized/fullscreen state when the answer is unknown. Ours can still pay repeated per-window timeouts and maps unreadable state to false. Adopt explicit unknown state and a refresh-scoped timeout budget, retaining our 250 ms focus query. Do **not** copy their elapsed-time >=90% heuristic as an authoritative timeout: a successful slow request can cross it. Surface actual AX errors instead. [Implementation][macapp]; [state handling][normalize]. |
| High | Window detection/rule completion | Their newly registered windows run the committed detection work in a cancellation shield, and apparent popups receive bounded rechecks after 1 and 3 seconds. Ours publishes the window in `allWindowsMap` before awaited restoration and callbacks; cancellation can leave a registered window whose rule sequence never finished, and popup promotion depends on later refreshes. Adopt a small, owned committed operation with window identity revalidation, plus coalesced bounded rechecks. Do not shield an entire refresh or let rules survive window destruction. [Registration][macwindow]; [commit #42][retry]. |
| High | Native-state mutation races | Their normalization re-reads state immediately before a tree-changing action, checks cancellation per window, and preserves MRU across native-state bookkeeping. Our generation guard prevents stale answers being cached, but the same returned snapshot is still placed in `axState` and can drive a mutation. The application loop also lacks per-window cancellation checks. Combine our cache with a fresh/version-validated decision before mutation and preserve MRU. Do not replace the cache with their always-prefetch-every-window approach. Tests should invalidate during an awaited read and between loop iterations, and assert tree/MRU outcomes. [Normalization][normalize]. This gap is established by static control-flow inspection; no live race reproduction was attempted. |
| High | Shutdown while MainActor is blocked | Their SIGTERM source runs on a separate queue and exits after a 10-second cleanup deadline, even if MainActor never services cleanup. Our source runs on `.main` after ignoring the default signal, so a blocked main queue can make SIGTERM ineffective. Keep our idempotent recovery/cleanup coordinator; add an independent signal deadline. Test in a subprocess with its main queue deliberately blocked. A forced exit cannot guarantee hidden-window restoration. [Termination implementation][termination]. |
| High, small change | Stack traces on every detach | They gate `getStringStacktrace()` behind optional diagnostics. Our `TreeNode.unbindIfBound()` calls it unconditionally; `getStringStacktrace()` invokes `Thread.callStackSymbols`. Every rebind pays symbolication to populate a diagnostic used for double-unbind failures. Adopt the gate and retain a useful fallback diagnostic. Verify logging-off does not call the stack supplier. This removes definite work; its user-facing latency benefit has not been measured. [Their TreeNode][treenode]; ours: `Sources/AppBundle/tree/TreeNode.swift:113`. |
| Medium | IPC input bounds and EOF | Their framing rejects payloads over 16 MiB, handles EOF, and puts a 30-second receive timeout on clients. Our `NWConnectionEx.read(bytes:)` preallocates from an unchecked length and loops on an empty successful receive without using `isComplete`; `readNonAtomic()` has no frame cap or read deadline. Keep Network.framework's asynchronous transport and current wire compatibility, and adopt explicit limits, EOF/cancellation handling and deadlines. Use socket-pair tests for partial headers, oversized frames, early close and silent peers. Their blocking wrapper is not an architectural upgrade. [Socket implementation][socket]; ours: `Sources/Common/util/NWConnectionEx.swift`. |
| Medium | Monitor fingerprints in explicit assignments | Their config accepts UUID and hardware fingerprints, with CoreGraphics-based identity and tests for identical panels. We already use UUID for saved-monitor restoration, but command/config monitor selection still exposes name/index/main/secondary only. Add UUID-based explicit targeting first; hardware fields only if needed. UUID mismatch must not silently choose another display. Keep ordinary selection ownership-preserving and movements explicit; do not import their automatic reconnect movement policy. [Fingerprint][fingerprint]; [resolver][resolver]. |
| Medium | State-file permissions | Their state write is serialized and applies owner-only `0600` permissions after atomic replacement. Our atomic state and backup writes do not set permissions; both installed files were observed at `0644` during this review. Adopt owner-only permissions for state **and backup**, including replacement writes. Our schema can include window titles/document metadata, so this is useful independently of restoration changes. Our writes are already ordered on MainActor; move encoding/writing off main only with an ordered worker and measurements. [State writer][memory]. |
| Medium | One validated config-write boundary | Their writer validates rendered bytes, preserves unmodeled content, refuses unsafe shapes and retains five backups. Our generic settings writer already parses before writing and serializes saves per model; however, shortcut/sidebar edit paths write separately, and the generic writer has no rotating backup. Consolidate the write/validation/backup contract, retaining our TOML-aware scalar editor. Do not replace it with their much larger writer or assume either design solves concurrent external-editor conflicts. [Config writer][writer]; [safety tests][writer-tests]. |

## Where we should keep our solution

| Area | Why WinMuxX is stronger or already equivalent |
| --- | --- |
| Refresh under event bursts | Our scheduler lets the active refresh finish, merges event requirements and runs one pending follow-up. Their 50 ms trailing debounce can defer work throughout a sustained stream, and its fired task cancels the active refresh. Their own notes describe a failed max-wait experiment that completed no layouts under a slow workload. Our light user-command sessions still cancel background work intentionally; this is not a claim of universal cancellation immunity. Keep our scheduler. [Their debouncer][debouncer]. |
| Hidden/live-window transitions | Their parking queues `setAxTopLeftCorner` and has no equivalent to our completed parking-before-reveal ordering, restore generation checks, position verification and build-69 WindowServer check before trusting a hidden flag. Their frame no-op guard is useful, but replacing our lifecycle would lose protections directly relevant to the Safari overlap bug. Keep ours; improve native fault-injection coverage. [Their parking code][macwindow]. |
| Restart restoration | Their memory restores window-ID-to-workspace/monitor membership within the same WindowServer session. It does not persist the complete tiling tree and split ratios. Ours saves the tree, ratios, monitor UUIDs, process identity and pending late arrivals, with backups and unique-match checks. Keep ours. Their strict refusal to guess between indistinguishable windows is a good invariant; our unique-match logic already rejects ambiguity, but its metadata-based cross-process matches still need continued regression coverage. Richer restoration is not proof of perfect identity. [Their memory][memory]. |
| Config file replacement/recreation | Our FSEvents directory watcher follows the link and target, observes recreation after deletion, and coalesces reloads without cancelling one already applying. Their watcher opens the individual file and re-arms after events; if it re-arms while the file is absent, it stops, with no parent watch to see a later creation. Keep ours. [Their watcher][watcher]. |
| Frame no-op checks | Both avoid AX writes when the requested frame already matches and put the guard before animation-disabling work. Their fake AX tests cover reads, ignored writes, clamping and failures more directly. Our restore path additionally verifies actual placement and supports position-first restoration. Keep our behavior; borrow their test seam. [AX tests][ax-tests]. |
| Tray publication | Both use equality guards before publishing unchanged menu state. There is no missing feature to import here. Their generic claim of “faster” does not establish a further gain for our implementation. |
| Workspace existence and display ownership | We already have persistent/minimum workspace policies, explicit relocation and ownership-preserving ordinary selection. Their declared-workspace fixes solve their own lifecycle contract; reconnect auto-movement conflicts with the user's explicit-move policy. Keep our policy and its multi-monitor tests. |
| Registration waiting | Their continuation waiters and our cancellation-aware broadcast latch both avoid polling. Replacing ours would add churn; the useful missing part is their failure/backoff policy. |

## Testing, dependencies and features

**Their AX mock is worth learning from.** `FakeAxElement` can accept, ignore, clamp or time out individual writes and count reads/writes. This exercises a lower boundary than our high-level fake window benchmarks. Introduce a narrow injectable native-access boundary where it provides real regression coverage; do not refactor every AX call merely to name an abstraction.

**Do not transplant source-text tests.** Several retry/unresponsive tests search function bodies for exact strings. These pin spelling and ordering, not the runtime outcome. Keep useful behavior tests and replace wiring assertions with controlled registration/AX dependencies and bounded expectations. Our own suite is not globally isolated either; it remains serial by design. Test counts alone do not decide which implementation is better.

**Do not copy the two-dependency target indiscriminately.** We already use a native networking framework rather than BlueSocket. Direct CoreAudio could remove a small sound wrapper after compatibility checks. Replacing HotKey requires preserving tap bindings, modes, recording and left/right modifier filtering. Removing our shell grammar or ordered collections may change behavior or move maintenance into handwritten code. None is a demonstrated speed win. Their fork intentionally drops some upstream configuration/commands; those removals are not fixes for WinMuxX.

No three-finger preview, dwindle, or modifier-side implementation comparable to ours was found in the inspected AeroSpork source. It offers no direct replacement for our swipe curve, snapshot preparation or cache lifecycle. Their documentation explicitly distinguishes work removed from measured user-facing speedups; we should keep that discipline. [Performance notes][performance].

## Recommended implementation sequence

1. Gate detach-time stack symbolication; add state/backup permissions. Small changes with clear boundaries.
2. Add app-registration backoff/retry and explicit unknown AX outcomes; preserve our latch and short focus timeout.
3. Fix normalization freshness/MRU and committed window-rule completion using behavior tests at the native boundary.
4. Add the independent shutdown deadline and IPC bounds/EOF/deadlines, each with isolated subprocess/socket tests.
5. Add UUID explicit monitor targeting and consolidate config write safety, preserving existing commands and user semantics.

For runtime changes: focused failing regressions first, `make check`, signed Release validation and relevant live checks. Measure warm latency separately from correctness; do not cite either fork's unit-test wall clock as desktop performance.
